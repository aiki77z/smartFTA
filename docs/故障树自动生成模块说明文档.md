# 故障树自动生成模块说明文档

本文档描述当前版本后端接口、知识发现逻辑、版本管理方式以及常见调用流程。内容已对齐当前代码实现，适用于：

- [main.py](/d:/fwwb/fault_tree_system/main.py)
- [database.py](/d:/fwwb/fault_tree_system/database.py)
- [generator.py](/d:/fwwb/fault_tree_system/generator.py)

## 1. 模块目标

当前系统的核心目标是：

1. 基于知识图谱和文档 chunk 生成故障树
2. 支持按 `file_id + file_version_id` 管理知识库
3. 支持会话级动态选源 `selected_file_version_ids`
4. 支持运行时局部子图拼接，不创建持久化图谱版本
5. 对每次生成结果保留可追溯证据

## 2. 当前知识与生成模型

### 2.1 知识来源

当前生成依赖两类核心数据：

- MongoDB 中的 `chunks`、`top_event_catalog`、`fault_trees`、`fault_tree_versions` 等集合
- Neo4j 中的 `Entity`、`Chunk`、`RELATION`、`MENTIONED_IN` 图数据

### 2.2 文件版本管理

系统只管理文件版本，不维护独立图谱版本表。

核心约束：

- 每个知识对象必须带 `file_id`
- 每个知识对象必须带 `file_version_id`
- 同一文件可有多个版本，但同一时刻只允许一个版本 `is_active = true`
- 删除文件时只做归档/失活，不立即物理删除

### 2.3 会话动态选源

所有与发现、召回、生成相关的接口都支持按 `selected_file_version_ids` 限定知识范围。

如果传入了 `selected_file_version_ids`：

- 顶事件匹配只在该范围内进行
- 子图扩展只在该范围内进行
- chunk 召回只在该范围内进行
- 树复用、任务去重也按该 scope 隔离

如果未传：

- 默认回退到当前 active 的文件版本范围

### 2.4 运行时子图拼接

当同名顶事件在多个 `file_version` 中同时存在时，系统会在当前 scope 内：

1. 找出所有命中的根节点
2. 扩展多个局部子图
3. 在内存中做运行时合并
4. 仅将合并结果用于本次生成

不会：

- 创建新的持久化图谱版本
- 把拼接后的图写回数据库

## 3. 顶事件发现逻辑

### 3.1 当前原则

顶事件发现不再把 `top_event_catalog` 当作唯一全集。

当前做法是：

1. 先从当前 scope 的图中发现顶事件候选
2. 再把候选结果和 `top_event_catalog` 合并去重
3. catalog 仅作为缓存、别名索引和补充信息来源

### 3.2 去重规则

顶事件候选以 `normalized_name` 为主键做合并，合并时保留：

- `name`
- `normalized_name`
- `aliases`
- `graph_node_ids`
- `file_ids`
- `file_version_ids`
- `source_chunk_ids`
- `support_count`
- `catalog_hit`
- `catalog_name`
- `discovery_sources`

### 3.3 批量生成与 scope 复用

`generate-all` 不按“顶事件同名”直接复用，而按以下键判断：

- `normalized_top_event`
- `source_scope_key`

含义：

- 同一 `top_event` + 同一 scope：可复用已有树
- 同一 `top_event` + 不同 scope：必须重新生成

这是为了保证不同文件版本组合下的结果互不串用。

## 4. 单树生成流程

接口：

- `POST /api/tree/generate`

流程：

1. 解析 `prompt`
2. 提取 `top_event` 与附加要求
3. 按当前 scope 匹配顶事件
4. 扩展局部子图或多根子图并做运行时拼接
5. 收集关联 chunk
6. 生成故障树 JSON
7. 进行修复与校验
8. 存储树版本及溯源信息

生成结果会保留：

- `source_file_version_ids`
- `evidence_chunk_ids`
- `subgraph_node_ids`

## 5. 批量生成流程

接口：

- `POST /api/batch/generate-all`

当前逻辑：

1. 发现当前 scope 下的顶事件全集
2. 补齐缺失的 catalog 条目
3. 对每个顶事件判断状态
4. 分类为：
   - `reused_in_same_scope`
   - `already_running_in_same_scope`
   - `queued_for_generation`
5. 仅对需要生成的条目创建任务

## 6. 接口总览

### 6.1 生成与调试

#### `POST /api/tree/resolve-top-event`

用途：

- 只解析 `prompt`，不直接生成故障树
- 返回当前 scope 下的精确命中结果，或返回候选顶事件供前端让用户选择

请求体示例：

```json
{
  "prompt": "请为我生成顶事件为XXX的故障树，要求给出主要原因",
  "selected_file_version_ids": ["fv_xxx_v1"],
  "candidate_limit": 10
}
```

返回重点字段：

- `status`
- `requested_top_event`
- `requirements`
- `resolved_top_event`
- `normalized_top_event`
- `graph_node_id`
- `candidates`

说明：

- `status = exact_match` 时，可直接调用 `POST /api/tree/generate`
- `status = need_user_confirmation` 时，前端应让用户从 `candidates` 中选择一个候选，再把确认结果带回 `generate`

#### `POST /api/tree/generate`
补充说明（2026-04 prompt 解析改造）：

- 请求体新增 `candidate_limit`
- 当用户已在前一步确认候选顶事件时，请把 `confirmed_top_event`、`confirmed_normalized_top_event`、`confirmed_graph_node_id` 一并传回
- 返回中的 `parsed_prompt` 现在包含 `requested_top_event`、`resolved_top_event`、`normalized_top_event`
- 若当前 scope 下没有精确命中，则接口直接返回 `mode = need_confirmation` 和候选列表，不再自动生成
- 若当前 scope 下还没有 `top_event_catalog`，接口会先自动重建目录，再做精确匹配和向量候选召回
- 若未配置 `EMBEDDING_MODEL` 或向量请求失败，候选召回会回退为基于名称的 lexical 排序

用途：

- 生成单棵故障树

请求体：

```json
{
  "prompt": "分析 XXX 故障",
  "selected_file_version_ids": ["fv_xxx_v1", "fv_yyy_v1"]
}
```

返回重点字段：

- `mode`
- `job_id`
- `item_id`
- `selected_file_version_ids`
- `parsed_prompt.top_event`
- `parsed_prompt.catalog_top_event`

说明：

- 若当前 scope 下已有可复用树，可能直接返回 `mode = reuse`
- 若当前 scope 下已有在跑任务，可能直接返回排队中的任务信息

#### `POST /api/debug/graph-recall`

用途：

- 调试顶事件解析、图匹配、局部子图扩展和 chunk 召回

请求体：

```json
{
  "top_event": "XXX 故障",
  "limit": 12,
  "selected_file_version_ids": ["fv_xxx_v1"]
}
```

或：

```json
{
  "prompt": "分析 XXX 故障",
  "limit": 12,
  "selected_file_version_ids": ["fv_xxx_v1"]
}
```

返回包含：

- `query`
- `catalog_entry`
- `graph_match`
- `subgraph`
- `chunk_recall`

适用场景：

- 检查当前 scope 下有没有正确命中顶事件
- 检查是否误用了未选中的版本
- 检查召回的 chunk 是否合理

### 6.2 顶事件发现

#### `POST /api/batch/preview-top-events`

用途：

- 预览当前 scope 下系统识别到的顶事件全集

请求体：

```json
{
  "limit": 200,
  "selected_file_version_ids": ["fv_xxx_v1", "fv_yyy_v1"]
}
```

返回重点字段：

- `discovery_source`
- `graph_total`
- `catalog_total`
- `total`
- `items`

每个 `item` 典型包含：

- `name`
- `normalized_name`
- `aliases`
- `graph_node_id`
- `file_version_ids`
- `support_count`
- `source_chunk_ids`
- `catalog_hit`
- `catalog_name`
- `discovery_sources`
- `graph_candidate_count`

#### `GET /api/catalog/top-events`

用途：

- 返回当前 scope 下合并后的顶事件目录视图

查询参数：

- `selected_file_version_ids`
  形式：`fv_a_v1,fv_b_v1`

返回重点字段：

- `items`
- `total`
- `selected_file_version_ids`
- `discovery_source`
- `graph_total`
- `catalog_total`

说明：

- 这个接口当前返回的是“发现结果 + catalog 补充”的合并视图
- 不再只是底层 `top_event_catalog` 集合的原样输出

#### `GET /api/top-events`

用途：

- 与 `/api/catalog/top-events` 类似，返回当前 scope 下的顶事件集合

查询参数：

- `limit`
- `selected_file_version_ids`

返回重点字段：

- `items`
- `total`
- `returned`
- `selected_file_version_ids`
- `discovery_source`
- `graph_total`
- `catalog_total`

### 6.3 批量生成

#### `POST /api/batch/generate-all`

用途：

- 对当前 scope 下全部发现到的顶事件进行批量调度

请求体：

```json
{
  "selected_file_version_ids": ["fv_xxx_v1", "fv_yyy_v1"]
}
```

返回重点字段：

- `job_id`
- `status`
- `discovered_total`
- `graph_total`
- `catalog_total`
- `existing_count`
- `active_count`
- `queued_count`
- `queued_item_ids`
- `items`

其中 `items` 为每个顶事件的状态列表，状态包括：

- `reused_in_same_scope`
- `already_running_in_same_scope`
- `queued_for_generation`

补充说明：

- 如果当前 `selected_file_version_ids` 对应的 scope 下已经存在未完成的 batch job，接口不会新建新的 job
- 此时会直接返回已有 `job_id`
- 返回中会带 `mode = existing_job`
- 同时会带 `continue_endpoint = /api/batch/job/{job_id}/continue`
- 前端应调用 continue 接口继续该 job，而不是重复新建同 scope 的 batch job

### 6.4 批量任务查询

#### `GET /api/batch/job/{job_id}`

用途：

- 查询批量任务状态及其子项

返回：

- `job`
- `items`

#### `GET /api/batch/job-item/{item_id}`

用途：

- 查询单个任务条目状态

返回重点字段：

- `status`
- `progress`
- `stage`
- `message`
- `events`
- `tree_id`
- `error`

#### `POST /api/batch/job/{job_id}/continue`

用途：

- 继续执行一个已有的 batch job

适用场景：

- 浏览器会话关闭后重新进入
- 后端重启后恢复未完成 batch job
- 用户想继续同一个 job，而不是新开同 scope 的重复 job

请求体：

```json
{
  "stale_after_seconds": 300
}
```

行为说明：

- `pending` 的任务项会重新入队
- `running` 的任务项如果超过 `stale_after_seconds` 未更新，会被判定为 stale 并重新入队
- 正在正常运行的任务项不会重复生成

返回重点字段：

- `job_id`
- `status`
- `selected_file_version_ids`
- `queued_item_ids`
- `queued_count`
- `stale_requeued_item_ids`
- `active_running_item_ids`

### 6.6 保存与修正

#### `POST /api/tree/{tree_id}/save`

用途：

- 保存人工修改后的故障树

请求体：

```json
{
  "tree_data": {},
  "editor": "专家",
  "description": "手动修改"
}
```

保存前会先做结构校验。

属性级修改会直接回写图节点属性，当前支持字段：

- `description`
- `errorLevel`
- `priority`
- `probability`
- `showProbability`
- `rule`
- `investigateMethod`

结构性变化不会直接改图结构，仍通过 `corrections` 机制学习。

返回重点字段：

- `success`
- `version`
- `learned_count`
- `graph_property_updates`

#### `GET /api/corrections/{tree_id}`

用途：

- 获取某棵树对应的 corrections 记录

### 6.7 校验接口

### 6.8 知识导入与文件管理

#### `POST /api/integration/import-knowledge-artifacts`

用途：

- 导入一个文件版本对应的知识产物

请求体：

```json
{
  "chunks_file": "D:/path/to/chunks.json",
  "entities_file": "D:/path/to/entities.json",
  "relations_file": "D:/path/to/relations.jsonl",
  "file_id": "file_test_part1_cleaned",
  "file_name": "test_part1_cleaned.md",
  "chunks_import_mode": "replace",
  "clear_graph": false,
  "import_relations": true,
  "source": "knowledge_base_construction"
}
```

说明：

- `file_id` 可选
  - 不传：新建文件
  - 传入：在原文件下创建新版本
- `clear_graph` 在当前版本化模式下禁止为 `true`
- 导入成功后会自动：
  1. 创建 `file_version`
  2. 导入 chunks
  3. 导入 entity reverse index
  4. 导入 Neo4j relations
  5. 重建该版本的 `top_event_catalog`
  6. 激活该版本

返回重点字段：

- `status`
- `file`
- `imported`
- `files`
- `next_steps`

#### `POST /api/files/{file_id}/archive`

用途：

- 归档文件

效果：

- `files.status` 置为归档
- 对应所有 `file_version` 失活
- 对应 chunks、catalog、图谱关系同步失活

## 7. 常见调用顺序

### 7.1 导入新知识文件

1. 调用 `POST /api/integration/import-knowledge-artifacts`
2. 调用 `POST /api/batch/preview-top-events`
3. 确认顶事件列表合理
4. 调用 `POST /api/batch/generate-all` 或 `POST /api/tree/generate`

### 7.2 调试单个顶事件

1. 调用 `POST /api/debug/graph-recall`
2. 检查顶事件匹配、子图、chunk
3. 再调用 `POST /api/tree/generate`

### 7.3 比较不同 scope 的生成差异

1. 用 scope A 调 `generate` 或 `generate-all`
2. 用 scope B 调 `generate` 或 `generate-all`
3. 对比版本中的：
   - `source_file_version_ids`
   - `evidence_chunk_ids`
   - `subgraph_node_ids`

## 8. 当前实现边界

当前已支持：

- 文件版本化知识管理
- 会话动态选源
- 运行时子图拼接
- 单树与批量生成
- 树复用与任务去重按 scope 隔离
- 顶事件发现与 catalog 合并
- 生成结果溯源
- 人工修改后的属性回写

当前仍未做的能力包括：

- 自动图结构回写
- 基于 embedding 的顶事件语义发现主链路
- 跨 scope 结果自动对比展示
- 更细粒度的候选顶事件人工审核工作流

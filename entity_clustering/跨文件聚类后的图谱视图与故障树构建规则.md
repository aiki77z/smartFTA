# 跨文件聚类后的图谱视图与故障树构建规则

本文档说明跨文件实体聚类完成后，知识图谱中的实体与关系应该处于什么状态，以及 GNR 在用户选择若干文件构建故障树时应该如何筛选当前可见视图。

## 1. 核心原则

`EntityCluster` 本身就是跨文件后的标准实体。一个 `EntityCluster` 可以由一个文件支持，也可以由多个文件共同支持。

同理，`EntityCluster` 之间的关系也可以由一个文件支持，也可以由多个文件共同支持。

GNR 构建故障树时，不应该默认查询全库，而必须根据用户当前选择的文件版本集合，筛选出“当前选择文件支持的图谱视图”。

## 2. EntityCluster 的状态

跨文件聚类后，逻辑上相同的实体会合并为同一个 `EntityCluster`。

例如：

```text
文件 A 中提到：实体1
文件 B 中提到：实体1
文件 C 中提到：实体1
```

图谱中只保留一个：

```cypher
(:EntityCluster {
  canonical_name: "实体1",
  source_file_ids: ["fileA", "fileB", "fileC"],
  source_file_version_ids: ["fileA_v1", "fileB_v1", "fileC_v1"],
  source_file_scopes: ["fileA::fileA_v1", "fileB::fileB_v1", "fileC::fileC_v1"]
})
```

实体的 `source_file_version_ids` 表示：哪些文件版本提供了这个实体本身的证据。

注意：一个实体可见，不代表它的所有关系都可见。

## 3. EntityCluster 关系的状态

关系也需要记录支持它的文件版本。

例如：

```text
文件 A 支持：实体1 -> 实体2
文件 B 支持：实体1 -> 实体3
文件 C 支持：实体1 -> 实体4
```

图谱中可以有：

```cypher
(:EntityCluster {canonical_name: "实体1"})
  -[:CLUSTERED_CAUSES {
    source_file_version_ids: ["fileA_v1"],
    relation_type: "CAUSES",
    relation_type_zh: "故障触发"
  }]->
(:EntityCluster {canonical_name: "实体2"})
```

```cypher
(:EntityCluster {canonical_name: "实体1"})
  -[:CLUSTERED_CAUSES {
    source_file_version_ids: ["fileB_v1"]
  }]->
(:EntityCluster {canonical_name: "实体3"})
```

```cypher
(:EntityCluster {canonical_name: "实体1"})
  -[:CLUSTERED_CAUSES {
    source_file_version_ids: ["fileC_v1"]
  }]->
(:EntityCluster {canonical_name: "实体4"})
```

关系的 `source_file_version_ids` 表示：哪些文件版本提供了这条关系的证据。

GNR 判断关系是否可见时，必须优先看关系自己的 `source_file_version_ids`。

## 4. 文件版本是视图过滤的基本单位

用户可能上传同一文件的新版本。

例如：

```text
文件 D: fileD_v1
文件 D 的新版本 E: fileD_v2
```

虽然它们可能共享同一个 `file_id`，但它们是不同的 `file_version_id`。

GNR 构建故障树时必须以 `file_version_id` 作为视图过滤的基本单位，而不是只看 `file_id`。

如果用户选择了 E，没有选择 D，那么只应该看到 `fileD_v2` 支持的实体和关系，不能看到只由 `fileD_v1` 支持的关系。

## 5. 故障树构建时的视图筛选规则

假设用户选择了：

```text
selected_file_version_ids = ["fileA_v1", "fileB_v1", "fileD_v2"]
```

那么 GNR 查询子图时，必须满足：

1. 关系由当前选择文件支持；
2. 关系两端实体也在当前选择文件中可见；
3. 每一跳扩展都带上同样的过滤条件。

推荐 Cypher：

```cypher
MATCH p=(a:EntityCluster)-[r]->(b:EntityCluster)
WHERE r.relation_level = "clustered"
  AND any(fid IN r.source_file_version_ids WHERE fid IN $selected_file_version_ids)
  AND any(fid IN a.source_file_version_ids WHERE fid IN $selected_file_version_ids)
  AND any(fid IN b.source_file_version_ids WHERE fid IN $selected_file_version_ids)
RETURN p;
```

最关键的是：

```cypher
any(fid IN r.source_file_version_ids WHERE fid IN $selected_file_version_ids)
```

因为实体可能被多个文件共同支持，但关系可能只来自其中某一个文件。判断某条边能否出现在当前故障树中，应以关系自己的证据文件范围为准。

## 6. 多跳扩展规则

故障树构建不是一次性查全库再裁剪，而应该在每一跳扩展时都带上视图过滤条件。

例如从顶事件出发，查 1 到 4 跳故障触发链：

```cypher
MATCH p=(top:EntityCluster {canonical_name: $top_event_name})-[rels:CLUSTERED_CAUSES*1..4]->(n:EntityCluster)
WHERE all(r IN rels WHERE any(fid IN r.source_file_version_ids WHERE fid IN $selected_file_version_ids))
  AND any(fid IN top.source_file_version_ids WHERE fid IN $selected_file_version_ids)
  AND any(fid IN n.source_file_version_ids WHERE fid IN $selected_file_version_ids)
RETURN p
LIMIT 200;
```

如果需要支持不同关系类型，可以写成：

```cypher
MATCH p=(top:EntityCluster {canonical_name: $top_event_name})-[rels*1..4]->(n:EntityCluster)
WHERE all(r IN rels WHERE r.relation_level = "clustered")
  AND all(r IN rels WHERE any(fid IN r.source_file_version_ids WHERE fid IN $selected_file_version_ids))
  AND any(fid IN top.source_file_version_ids WHERE fid IN $selected_file_version_ids)
  AND any(fid IN n.source_file_version_ids WHERE fid IN $selected_file_version_ids)
RETURN p
LIMIT 200;
```

## 7. 示例

假设：

```text
A 中有：实体1 -> 实体2
B 中有：实体1 -> 实体3
C 中有：实体1 -> 实体4，实体2 -> 实体5
D 中有：实体2 -> 实体6
E 是 D 的新版本，E 中有：实体2 -> 实体7
```

用户构建故障树时选择：

```text
A, B, E
```

顶事件：

```text
实体1
```

那么当前故障树中应该出现：

```text
实体1
实体2
实体3
实体7
```

应该出现的关系：

```text
实体1 -> 实体2  来自 A
实体1 -> 实体3  来自 B
实体2 -> 实体7  来自 E
```

不能出现：

```text
实体4
实体5
实体6
```

不能出现的关系：

```text
实体1 -> 实体4  来自 C
实体2 -> 实体5  来自 C
实体2 -> 实体6  来自 D
```

原因：

- C 没被选择，所以 C 支持的实体关系不可见；
- D 没被选择，即使 E 是 D 的新版本，也不能看到只由 D 支持的关系；
- E 被选择，所以 E 支持的 `实体2 -> 实体7` 可见；
- 实体1 虽然可能被 A/B/C 共同支持，但 `实体1 -> 实体4` 这条关系只由 C 支持，所以不能进入当前故障树。

## 8. MongoDB 查询范围

MongoDB 中也需要按当前选择文件版本过滤。

顶事件候选：

```javascript
db.top_event_catalog.find({
  source_file_version_ids: { $in: selected_file_version_ids }
})
```

chunks：

```javascript
db.chunks.find({
  file_version_id: { $in: selected_file_version_ids }
})
```

如果当前临时数据中 `top_event_catalog` 还只保存单个 `file_version_id` 字段，也应该在后续跨文件聚类改造时补充：

```text
source_file_ids
source_file_version_ids
source_file_scopes
```

## 9. 实现建议

跨文件聚类改造后，导入图谱时需要保证：

1. `EntityCluster.source_file_version_ids` 是数组，不是单值；
2. `CLUSTERED_*` 关系的 `source_file_version_ids` 也是数组；
3. 合并实体时，把新文件的 Mention 继续通过 `RESOLVED_TO` 指向同一个 EntityCluster；
4. 合并关系时，不重复建边，而是合并 `source_file_version_ids`、`evidence_json`、`source_relation_ids`；
5. GNR 查询时不要只按实体过滤，必须按关系自己的 `source_file_version_ids` 过滤边。

一句话总结：

**跨文件聚类让 EntityCluster 成为全局标准实体；用户选择文件时，GNR 通过实体和关系的支持文件版本数组裁剪出当前文件视图。**

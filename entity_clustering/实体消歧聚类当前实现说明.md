# 实体消歧聚类当前实现说明

本文档记录 `FTA-KB/entity_clustering/` 中实体消歧聚类模块的当前实现、调试方式，以及 SUN2000 / LUNA2000 两组标注数据的测试结果。

## 1. 模块目标

微调后的抽取模型会输出 `[ENTITY] / [RELATION] / [LOGIC_GROUP]`。同一真实实体可能在不同 chunk 中以不同 mention 出现，例如“绝缘阻抗低”和“绝缘阻抗变低”，因此需要在导入最终实体图谱前完成：

1. 保留每次抽取到的 mention 实例；
2. 在同一文件内对 mention 做实体消歧与聚类；
3. 生成标准实体簇 `SmartFTAEntityCluster`；
4. 将 mention 级关系聚合为实体簇之间的关系；
5. 将 chunk、mention、entity cluster 和聚合关系导入 Neo4j，便于查看、调试和后续故障树构建。

## 2. Neo4j 图结构

当前 mention 与聚类后的实体簇保存在同一个 Neo4j 图中，但使用不同标签。

主要节点：

| 节点 | 含义 |
|---|---|
| `SmartFTAChunk` | chunk 节点，保存 chunk 归属与文本定位信息 |
| `SmartFTAMention` | 模型抽取出来的原始实体提及，保留原始名称、类型、证据、chunk 信息 |
| `SmartFTAEntityCluster` | 消歧聚类后的标准实体簇，代表同一真实实体 |

主要关系：

| 关系 | 含义 |
|---|---|
| `(Mention)-[:EVIDENCED_IN]->(Chunk)` | mention 的证据来源 |
| `(Mention)-[:RESOLVED_TO]->(EntityCluster)` | mention 被聚类到哪个标准实体簇 |
| `(EntityCluster)-[:故障触发/故障处理/故障表征/规则触发/...]->(EntityCluster)` | mention 级关系聚合后的实体簇级关系 |

当前不导入 `File` 节点，也不把关系保存成单独 relationship 节点。

## 3. 聚类流程

### 3.1 解析模型输出

入口函数主要在 `cluster_entities.py`：

- `load_mentions_and_relations()`：从审核后的 CSV 中读取 `assistant` 输出，解析 `[ENTITY] / [RELATION] / [LOGIC_GROUP]`。
- `[ENTITY]` 会转换为 `Mention`。
- `[RELATION]` 会先保存为 mention 级原始关系，再通过端点名称解析到 source / target mention。

每个 mention 主要保存：

- `mention`：模型输出的实体表述；
- `normalized_name`：模型输出或规范化后的实体名；
- `entity_type`：故障事件、维修方法、报警码、触发规则等；
- `evidence`：证据数组，包含 `chunk_id / text_field / start / end / text`；
- `chunk_ids`：该 mention 出现在哪些 chunk 中；
- `neighbor_tokens`：关系邻居和局部上下文邻居；
- `embedding`：可选向量表示。

### 3.2 mention-level graph 信息

当前没有单独维护一个 mention-level graph 数据库，而是在内存中为 mention 构造邻居特征，并在 Neo4j 中保留 mention 节点。

邻居特征包括：

- 关系邻居：来自 `[RELATION]` 的 source / target 端点，例如 `out:故障处理:故障事件:xxx`。
- 局部上下文邻居：同一 chunk 或相邻 chunk 中共同出现的实体，作为弱邻居。

这些邻居不额外导入 `CO_OCCURS_WITH` 边。需要查看共现时，可以通过共同 `EVIDENCED_IN` 的 chunk 或 mention 属性检索。

### 3.3 embedding

当前支持 DashScope 兼容 OpenAI 的 embedding 接口，例如：

```text
EMBEDDING_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
EMBEDDING_MODEL=text-embedding-v4
```

embedding 用于：

- 召回名称不完全一致但语义接近的候选实体簇；
- 计算 mention 与 cluster 的语义相似度；
- 辅助 soft neighbor similarity，即邻居名称不完全一致但语义相近时仍可得分。

embedding 会缓存到：

```text
entity_clustering/output/<dataset>/entity_embeddings.jsonl
```

后续重复聚类可使用 `--reuse-embeddings-jsonl`，避免重复调用 API。

### 3.4 候选召回与 TopK 过滤

当前已经加入候选召回层，避免 refinement 对所有 mention-cluster 组合暴力计算。

函数：

```text
rank_candidate_clusters()
```

候选召回条件：

1. 同 `file_id`、同 `entity_type`；
2. 先排除 `hard_conflict`；
3. 满足以下任一初筛条件才进入候选：
   - `name_score >= 0.45`
   - `embedding_score >= 0.88`
   - `neighbor_score >= 0.35`
4. 每个 mention 最多保留 `TopK=20` 个候选 cluster；
5. 只有 TopK 候选才进入完整 `cluster_score()`。

对应参数：

```powershell
--candidate-top-k 20
--candidate-min-name 0.45
--candidate-min-embedding 0.88
--candidate-min-neighbor 0.35
```

### 3.5 综合打分

核心函数：

```text
cluster_score()
```

当前基础公式：

```text
score =
  0.55 * name_score
  + 0.20 * embedding_score
  + 0.20 * neighbor_score
  + 0.05 * chunk_score
```

其中：

- `name_score`：规范化名称的字符串相似度；
- `embedding_score`：mention 与 cluster 向量余弦相似度；
- `neighbor_score`：soft neighbor similarity，不要求邻居完全相同，只要方向、关系类型、实体类型和邻居名称相似即可得分；
- `chunk_score`：是否出现在同一或相邻 chunk 的弱加分。

此外还有两类 boost：

- `graph_boost`：关系邻居高度一致时提高合并倾向；
- `semantic_boost`：名称和 embedding 双高时提高合并倾向。

### 3.6 硬冲突与保守规则

为了避免语义相反或对象不同的 mention 被误合并，当前加入了多类硬冲突与保守判断。

已支持：

- 报警码严格匹配：`3027` 与 `3027-4` 不合并；
- 触发规则阈值冲突：阈值、持续时间等不同则不合并；
- 高/低、开/关、正常/异常等状态冲突；
- 交流/直流、输入/输出、正极/负极等工业方向冲突；
- 北向/南向、上行/下行、入站/出站、内部/外部等方向或链路限定符冲突；
- 编号冲突：如 `温湿度传感器-1通信故障` 与 `温湿度传感器-2通信故障` 不合并；
- 未解释特异对象冲突：如 `PCS与SmartLogger之间通信线异常` 与 `CMU与SmartLogger之间通信线异常` 不合并；
- 维修方法对象槽冲突：如 `更换环境温度传感器`、`更换冷凝器温度传感器`、`更换蒸发器温度传感器` 不合并；
- 名称最小差异片段冲突：如 `簇内快速关机接线错误` 与 `簇间快速关机接线错误`，公共部分高度一致但差异片段承载关键语义，因此不合并。

最近一次优化后，`evidence` 不再被过度用作硬冲突来源：

- 如果实体名 / canonical name 本身存在关键差异，直接禁止合并；
- 如果只是 evidence 中出现输入/输出、交流/直流差异，但两个实体名本身都是泛化表达，则不再仅因为 evidence 差异禁止合并；
- 如果 mention 同时有具体原始名和泛化 `normalized_name`，只要泛化名与 canonical name 能安全匹配，就允许继续走 score 判断。

因此：

- `确认断路器及供电开关位置`
- `确认断路器及开关位置`

现在可以合并；但：

- `簇内快速关机接线错误`
- `簇间快速关机接线错误`

仍会被拆开。

### 3.7 第一轮聚类

`cluster_mentions()` 会按 `file_id + entity_type` 分桶，只在同文件、同实体类型内聚类。

主要步骤：

1. 优先检查完全一致的规范化名称或已有 alias；
2. 使用 `rank_candidate_clusters()` 召回 TopK 候选；
3. 对候选 cluster 计算 `cluster_score()`；
4. 分数超过 `auto_threshold` 时自动合并；
5. 低于自动阈值但超过 `review_threshold` 的候选写入诊断文件；
6. 无法确认时保留为独立实体簇。

### 3.8 refinement 二次聚类

第一轮聚类后，部分应合并 mention 可能因为当时还没有稳定邻居或 alias 而没有合并，因此实现了 refinement。

`refine_clusters()` 会：

- 对 mention 与其他同文件、同类型 cluster 做二次检查；
- 先通过 TopK 候选召回缩小候选范围；
- 再调用 `cluster_score()` 和 `refine_candidate_merge_reason()` 判断是否合并；
- 默认模式为 `single`，每轮只合并一个最可信候选，较保守；
- `batch` / `strong-batch` 保留为实验模式，目前不建议作为默认导入策略。

当前主要瓶颈仍在 refinement 和 debug 的高分未合并扫描。TopK 已经降低了候选数量，但 soft neighbor 和代表 mention 分数计算仍然比较耗时。

## 4. 实体簇代表名选择

聚类后需要选择一个 `canonical_name` 作为实体簇代表名称。

当前不是简单取第一个 mention，而是综合：

- 名称长度是否适中；
- 维修动作是否完整；
- 对象描述是否完整；
- 是否覆盖更多证据与关系；
- mention 在簇内与其他 mention 的中心性。

例如：

- `检查簇控制器电池侧功率线及通讯线连接`
- `检查功率线及通讯线连接`

这两个 mention 可以合并，但代表名更倾向选择信息更完整的：

```text
检查簇控制器电池侧功率线及通讯线连接
```

## 5. 当前运行命令

在 `FTA-KB` 目录下运行，并使用 `FTA-KB/.venv`：

```powershell
.\.venv\Scripts\python.exe entity_clustering\import_cluster_graph_to_neo4j.py `
  --env-file entity_clustering\.env `
  --input-csv "..\annotation-data-pipeline\zyt\HUAWEI LUNA2000-(97KWH-200KWH)系列 工商业构网型储能系统 告警参考_organized.csv" `
  --file-id huawei_luna2000_alarm_reference `
  --output-dir entity_clustering\output\luna2000_dashscope `
  --embedding-backend openai-compatible `
  --reuse-embeddings-jsonl entity_clustering\output\luna2000_dashscope\entity_embeddings.jsonl `
  --refinement-max-rounds 8 `
  --candidate-top-k 20 `
  --candidate-min-name 0.45 `
  --candidate-min-embedding 0.88 `
  --candidate-min-neighbor 0.35
```

说明：

- `--reuse-embeddings-jsonl` 表示复用已有 embedding；
- `--refinement-max-rounds 8` 是当前较稳妥的调试参数；
- 不建议直接把 refinement 轮数拉到很高，否则运行时间会明显增加；
- 默认 `single + TopK` 是当前推荐策略。

## 6. Debug 命令

查看已合并样例、未合并高分候选和诊断候选：

```powershell
.\.venv\Scripts\python.exe entity_clustering\debug_cluster_scores.py `
  --output-dir entity_clustering\output\luna2000_dashscope `
  --merged-limit 10 `
  --unmerged-limit 60 `
  --scan-unmerged-pairs `
  --scan-limit 100 `
  --scan-min-score 0.50 `
  > entity_clustering\output\luna2000_dashscope\debug_cluster_scores.txt
```

当前 `debug_cluster_scores.py` 的未合并扫描也已改为 TopK 候选扫描，而不是全量 pairwise 扫描。

注意：

- `--scan-limit` 控制最终输出条数；
- `--scan-candidate-top-k` 控制每个 mention 扫描多少个候选 cluster，默认 20；
- PowerShell 重定向出来的 `debug_cluster_scores.txt` 通常是 UTF-16 编码，可直接用 VS Code 打开；
- LUNA2000 当前规模下，这个 debug 扫描仍可能运行数分钟。

## 8. 当前问题与后续优化方向

### 8.1 refinement 性能

TopK 已经减少了候选范围，但 refinement 和 debug 扫描仍会调用较多次：

```text
name_score + embedding_score + soft_neighbor_similarity + cluster_score
```

后续可以继续优化：

1. 对 soft neighbor similarity 加更强缓存；
2. 在 debug 扫描中只输出候选簇，不再为候选簇寻找最相近代表 mention；
3. 为每个 bucket 预先建立 embedding 近邻索引；
4. 对明显低信息的泛化维修方法引入更细的“泛化实体/具体实体”层级，而不是简单合并或拆分。

### 8.2 高分未合并候选

`debug_cluster_scores.py --scan-unmerged-pairs` 中仍可能出现高分未合并候选。原因包括：

- 调试脚本是事后扫描，不完全等同于真实聚类过程中的 mention-to-cluster 判断；
- 默认 refinement 仍较保守；
- 某些候选虽然分数高，但存在方向、状态、编号或对象差异，应当被硬冲突挡住；
- 某些候选属于“泛化实体”和“具体实体”的层级关系，是否合并需要结合项目图谱设计决定。

### 8.3 跨文件实体聚类

当前聚类范围是同一 `file_id` 内。后续如果需要跨文件聚类，建议分两阶段：

1. 文件内聚类：先在每个文件内得到高质量实体簇；
2. 文件间聚类：再对实体簇做二次聚类，比较 `canonical_name / aliases / embedding / 类型 / 设备系统 / 关系邻居`。

跨文件聚类应比文件内聚类更保守，尤其是报警码、触发规则、设备对象限定词不同的情况。
